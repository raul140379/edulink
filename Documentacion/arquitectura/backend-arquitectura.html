Documento de referencia técnica

Arquitectura del backend de EduLink

Cómo está organizado el backend después del refactor por capas: de dónde viene, cómo fluye una petición HTTP de principio a fin, y qué responsabilidad tiene cada pieza. Sirve de mapa antes de profundizar capa por capa en sesiones futuras.

📍 EduLink/backend 🧱 Node · Express · TypeScript · Prisma · PostgreSQL 🔁 ~24 dominios refactorizados

§1 Resumen

EduLink nació como una copia aislada de sgje (el sistema en producción de la U.E. Naciones Unidas El Torno) para poder refactorizar el backend sin riesgo. El backend original mezclaba todo en el controller: rutas, reglas de negocio y consultas a Prisma en el mismo archivo. Se migró, dominio por dominio, a una arquitectura en capas donde cada archivo tiene una única responsabilidad.

antes

Todo en el controller

Validación manual, reglas de negocio y prisma.* mezclados en la misma función. Permisos inconsistentes o ausentes.

después

Cinco responsabilidades separadas

Ruta → validación → controller delgado → servicio → repositorio. Un único lugar de verdad para permisos y para acceso a datos.

§2 Estructura de carpetas

Un archivo por dominio, en cada una de las cinco carpetas de capas, más cuatro carpetas de soporte transversal.

backend/src/
// una carpeta por capa — el nombre del archivo es siempre el dominio
config/          permissions.ts · env.ts
middlewares/     auth.middleware.ts · validate.middleware.ts
routes/          meeting.routes.ts, treasury.routes.ts, ...
controllers/     meeting.controller.ts, treasury.controller.ts, ...
services/        meeting.service.ts, treasury.service.ts, ...
repositories/    meeting.repository.ts, treasury.repository.ts, ...
schemas/         meeting.schema.ts, treasury.schema.ts, ...
utils/           http-error.ts · account-generator.ts
lib/prisma.ts    cliente Prisma, instancia única

§3 Flujo de una petición

Toda petición HTTP atraviesa las mismas seis etapas, en el mismo orden, sin excepciones.

1
Ruta recibe la peticiónDefine método + URL, encadena los middlewares en orden
routes/*.routes.ts
2
verifyTokenDecodifica el JWT, adjunta req.userId / req.role
middlewares/auth.middleware.ts
3
requirePermission(...)Consulta ROLE_PERMISSIONS; corta con 403 si el rol no lo tiene
middlewares/auth.middleware.ts
4
validateBody(schema)Corre el schema de Zod contra req.body; 400 con detalle si falla
middlewares/validate.middleware.ts
5
ControllerLlama al service, traduce el resultado a res.json() / status
controllers/*.controller.ts
6
Service → Repository → PrismaReglas de negocio, luego la única capa que toca la base de datos
services/ · repositories/

§4 Las capas

Cada capa tiene una regla de una sola línea que decide qué puede y qué no puede contener.

Routes

Regla: define URL + método + qué middlewares aplican. Nunca contiene lógica.

routes/meeting.routes.ts
router.post('/',
  requirePermission(Permission.MEETING_CREATE),
  validateBody(createMeetingSchema),
  createMeeting
)

Middlewares

Regla: cortan la petición antes de llegar al controller si algo no cumple; nunca contienen reglas de negocio del dominio.

auth.middleware.ts

verifyToken / requirePermission / requireRole

Autenticación (¿quién sos?) y autorización (¿podés hacer esto?). Es el único lugar del backend que decide permisos.

validate.middleware.ts

validateBody(schema)

Corre schema.safeParse(req.body); en error responde 400 con { errors: [{ field, message }] }.

Controllers

Regla: solo llama al service y traduce el resultado a HTTP. Sin prisma.*, sin condicionales de negocio.

controllers/meeting.controller.ts
export const createMeeting = async (req, res) => {
  try {
    const meeting = await meetingService.createMeeting(req.userId, req.body)
    res.status(201).json({ message: 'Reunión creada correctamente', meeting })
  } catch (error) { handleControllerError(res, error) }
}

Services

Regla: toda la lógica de negocio vive acá — validaciones cruzadas, cálculos, orquestar varias llamadas al repositorio. Lanza HttpError cuando algo no cumple una regla.

services/meeting.service.ts
async createMeeting(userId, input) {
  const parent = await meetingRepository.findParentWithDelegateCourseAssignments(userId)
  if (!parent || !parent.delegateCourse)
    throw new HttpError(404, 'No tienes un curso asignado como delegado')

  const parentIds = collectTutorIds(parent.delegateCourse.assignments)
  return meetingRepository.createMeeting({ ...input, courseId: parent.delegateCourse.id, parentIds })
}

Repositories

Regla: el único lugar que importa prisma. Sin if de negocio — solo consultas parametrizadas.

repositories/meeting.repository.ts
createMeeting(data) {
  return prisma.meeting.create({
    data: {
      title: data.title, date: data.date, courseId: data.courseId, createdById: data.createdById,
      attendances: { create: data.parentIds.map(parentId => ({ parentId, present: false })) },
    },
  })
}

Piezas transversales

config/permissions.ts

Role, Permission, ROLE_PERMISSIONS

Única fuente de verdad de autorización: qué permiso tiene cada rol. Nunca se decide un permiso dentro de un controller o service.

config/env.ts

Variables de entorno

Centraliza PORT / JWT_SECRET; exige el secreto explícito en producción.

utils/http-error.ts

HttpError · handleControllerError

Vocabulario común de error entre service y controller: throw new HttpError(status, mensaje) se traduce siempre igual.

utils/account-generator.ts

Emails y contraseñas por defecto

Compartido entre student / teacher / parent service para no duplicar la generación de credenciales.

lib/prisma.ts

Cliente Prisma único

Una sola instancia reutilizada en todo el backend — nunca new PrismaClient() dentro de un controller.

§6 Sistema de permisos

Cada rol tiene una lista fija de permisos en ROLE_PERMISSIONS. requirePermission(P) simplemente verifica si ROLE_PERMISSIONS[req.role] incluye P.

config/permissions.ts
export const hasPermission = (role, permission) => {
  const permissions = ROLE_PERMISSIONS[role]
  return permissions?.includes(permission) ?? false
}

Durante la migración, este fue el hallazgo más repetido: la mayoría de rutas no tenían requirePermission, o reutilizaban un permiso sin relación (ej. USER_CREATE para gestionar horarios). Se creó un permiso dedicado por dominio cuando hacía falta, siempre confirmando primero — con grep sobre el frontend — qué rol realmente usa cada endpoint.

§7 Metodología de migración

El mismo ciclo de 8 pasos, repetido para cada uno de los ~24 dominios.

1 · Leer el original

Controller completo, sin asumir nada.

2 · Auditar permisos

Revisar routes.ts contra el uso real en frontend.

3 · Crear las capas

schema → repository → service → controller delgado.

4 · Compilar

tsc --noEmit antes de cualquier prueba.

5 · Probar en vivo

Contra edulink_dev, un espejo real de producción.

6 · Verificar 403/409

Confirmar que el rol equivocado es rechazado.

7 · Limpiar

Revertir contraseñas y borrar datos de prueba, siempre.

8 · Documentar

Hallazgos a memoria persistente entre sesiones.
